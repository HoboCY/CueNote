2026-10-18，针对 #33 的 [第六轮完整矩阵](performance-macos-matrix6.md) 中普通保存 p95 3,076.09 ms 超过 2 秒的问题进行诊断。应用仍为 `cbd9c08293830652a2cdf066b537bbcec8481ff6`，驱动源码为 `d772644ac60e8fc6285ffbd4e8c7d5cb0686eb77`。使用已有的独立合成千篇库，启用 `CUENOTE_PERF_TRACE=1`；这些记录不计入正式 Q51 成绩，也不替代修复后的完整矩阵。

## 系统栈采样

第二次尝试在保存和采样开始前遇到原生鼠标操作的观察响应超时，记录 0 次保存；应用随后正常退出，状态 0。失败证据保留。

第三次尝试从已选普通笔记的图片就绪状态开始，完成 16 次保存；同时用系统 `/usr/bin/sample` 按 5 ms 间隔采样 25 秒，采样工具和应用均正常退出。采样及诊断改变了负载，第三次的时间只用于定位，不能与无采样矩阵直接比较。

调用栈表明：

- 保存后的扫描主要在等待文件核验工作线程；工作线程包含完整 SHA、读取及等待新任务的路径。等待接收队列时仍持有 receiver Mutex，不能据此认定哈希被该锁串行化，也不能将 `read` 栈直接解释为物理磁盘饱和。
- 原生保存中的 `preserve_observed_version → rotate_observed_versions_locked → read_stored_version → inspect_note` 占有明显采样，涉及完整包解析、复制和校验。它与扫描中少量的重复版本保留是两处不同开销。
- 这些是跨线程、跨多轮操作的驻留采样，不是单次墙钟时间或 CPU 百分比。当前数据还不足以断言 16 项任务窗口造成队首阻塞。

下一步先关联一轮保存的扫描任务时间轴、源文件与独立版本副本核验耗时、工作线程活动数，以及轮换成员数和完整解析耗时。现阶段没有减少完整 SHA 校验、改变最近 30 份有效历史保留规则，或放宽任何性能门槛。

## 第四次：分段与任务时间轴

随后用 `90ce940` 诊断构建在同一合成库完成四次普通保存，未运行系统栈采样；应用正常退出，状态 0。这仍是开启追踪的定位记录，不计入 Q51。原生安全保存耗时 605–1,007 ms，保存后库扫描耗时 990–1,381 ms，工作区锁等待均低于 0.015 ms。

每次历史轮换检查 31 个有效成员，删除 1 个；第一遍完整解析合计耗时 298–560 ms，删除前再次完整检查耗时 9–16 ms。保持当前完整文件 SHA、元数据与删除前校验的前提下，重复解析是一个可独立验证的优化候选。

四次保存扫描各完整检查 1,000 项。8 个工作线程的平均活动任务数为 2.10–2.49，单任务活动区间累计 359–493 ms；最长等待对应约 52.4 MB 的压力包，其前方已安排的范围止于当前项加 16，等待结束时只剩 0 或 1 个任务活动。这表明当前有界预取窗口存在利用率不足；活动时间是任务驻留时间，不能解释为 CPU 使用率。下一步先做单变量、有界对照，不跳过源文件或独立版本副本的完整 SHA。

原始归档 `mac-save-profile-4-20261018.tar.gz` 含 21 个文件，SHA-256 为 `f6c7c674c381a539c8caf1c67d5164dbd919344048d27c666d7e440660f5bd13`。原始日志包含六次完整扫描（四次由保存触发）和四次轮换，下载后全部文件摘要已校验。
