# 同步文件的本机处理契约

对应 [#24 应对 OneDrive 按需文件与组织信息乱序到达](https://github.com/HoboCY/CueNote/issues/24)，沿用 [原生文件 ADR](adr/0002-portable-note-files.md) 和 [#23 外部变化契约](external-changes-contract.md)。本项处理文件已经或尚未到达本机时的应用行为，不实现云账号、上传队列或同步引擎；实际双端下载、断网与重连由 #33 验收。

## 可用性与内容保护

界面提示把整个笔记库设为始终保留本机。保存结果只代表本机文件，不显示未经验证的云端同步完成。未下载、云盘校验尚未完成、不可读或损坏的文件不能解释为新建空笔记或空笔记本；来源恢复可读后允许重新核对。

Windows 在读取内容前检查离线与按需取数属性；对于重解析文件，通过句柄取得属性及 tag，只认可 Cloud Files tag 家族并交由系统解析状态。完整可读的云盘文件可以继续使用；链接、目录联接和未知 tag 仍被拒绝。`PARTIAL` 表示尚不可供应用读取，不一概声称还在下载；`IN_SYNC` 不用作本机可编辑条件。目录祖先仅作身份固定时不要求其所有无关子文件均已下载。

macOS 在文件或目录内容访问前检查 dataless 状态，并在同步宿主操作所在的线程禁止隐式物化，操作结束恢复原策略。Windows/macOS 均保留格式校验、读取预算、指纹和独立恢复副本。应用不修改用户文件的下载属性来强制使其可读。

本机恢复区、设置和暂存目录继续使用原来的严格路径边界；对同步事实文件允许已验证的云盘对象，不等于放宽这些本机目录的重解析限制。

平台依据：[Microsoft 文件属性](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants)、[Cloud Files 状态解析](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetplaceholderstatefromattributetag)、[占位状态含义](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_placeholder_state)、[Apple TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files)、[Darwin 错误码定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/errno.h)。

## 组织信息到达顺序

每篇笔记仍保存原笔记本身份、置顶和回收站状态；每个笔记本仍有独立 JSON，空笔记本不依靠笔记推断。界面偏好只写本机设置目录。

笔记先到而元数据缺失时，保留所选库和可读笔记，未知归属以只读方式展示，不补造身份、不把笔记转到默认本。默认笔记本尚未确认时使用可空字段，依赖该身份的写入操作需等待。已有空目录的首次建库使用明确初始化入口，并由宿主验证没有笔记、元数据或不可读内容；刷新不自动把同步中的空目录初始化为另一个库。

文件事件、启动和重新聚焦重新读取元数据。仅有笔记本信息变化时，前端只更新当前同一会话的只读原因，不替换正文、草稿或撤销历史，也不虚构内容冲突。目录整体暂不可读时保留可见快照并提示；具体坏文件或冲突文件保留原路径、说明原因，不自动挑选某个名称合并。

已经进入外部冲突保护的会话继续由冲突流程处理，不把其只读原因当作元数据缺失。即使笔记暂时只读，用户仍可明确选择在保护当前草稿后继续切换或关闭；文件恢复本身不等于同意丢弃当前内容。

组织写入前核对当前磁盘事实。笔记本重命名与删除比较用户看到的版本和磁盘版本，不能先悄悄刷新基线再覆盖。发布前已发现变化时不修改目标；若外部更新恰好发生在最后一次核对与系统原子操作之间，则核对实际被移出的版本，保留双方文件并报冲突。文件系统没有对不参与应用锁的同步程序提供按内容比较后交换的事务，因此不承诺目标路径从未短暂改变；遇到不确定结果也不通过覆盖目标回滚。

元数据保留文件使用同目录可被扫描发现的 JSON，重新打开库仍会提示路径。这些文件也可能来自失败或中断的操作，不一概表示已发生外部冲突；应用不将它们加载为额外笔记本，也不自动清理。发布失败时保留本次请求的名称等元数据；删除期间发现原路径重新出现时保留双方并报告冲突。笔记本名称相同而身份不同的条目显示身份短码以便区分，仍分别保留各自归属。笔记改名副本和重复身份的不同内容沿用 #23 的独立完整保留版本、只读打开、恢复新笔记和另存入口。

发布已经校验、同步成功后，旧元数据副本的清理若无法完成目录同步，仍会报告清理错误；这时新版本已在正式路径，不能把该错误一概解释成改名未生效，也不承诺已清理的独立副本还存在。重新检查文件更新可确认当前名称。

永久删除回收站笔记时，先将实际文件无覆盖移到同目录的唯一 `.cuenote` 路径，再核验身份、版本和回收站状态。外部换入的不同版本只尝试无覆盖恢复；原路径已有文件或结果不确定时保留隔离文件并提示。清理前发现原路径重新出现也保留双方。若进程在隔离后退出，重新打开库会发现该文件，并沿用“历史与冲突”入口提供只读查看及恢复。该操作不锁住 OneDrive，最后一次检查后仍可能有后续文件到达。

## 验证边界

使用已约定的公共 Workspace/存储接口与隔离目录，按不同次序投放、移走和恢复实际文件；前端通过既有会话/IPC 协调边界验证。Windows 普通测试文件的 `OFFLINE` 属性只用于验证不可用分流，不等于运行了 OneDrive provider；不注册测试云盘提供程序，不操作用户 OneDrive。具体结果见 [验证记录](sync-files-validation.md)。
